⏮️ Before & trade-offs

Every tool replaced something worse — and is itself the wrong tool somewhere. For each big idea: what life was like before, honest merits ✅ / demerits ❌, and where to use it 👍 vs not 👎.

🍦 Vanilla JS vs a framework — lessons 05, 07

⏮️ Before frameworks (jQuery era, ~2010)

Pages were edited by hand: find the element, change its text, remember to update the three other places that show the same number. State lived in the DOM and nowhere else — and drifted.

✅ Merits

  • vanilla: zero build, zero bytes, nothing to upgrade; fine for boards and widgets
  • framework: state → view for free, components, an ecosystem of parts

❌ Demerits

  • vanilla: you write render() and diffing yourself as the app grows
  • framework: build steps, bundle weight, version churn, hiring by framework

👍 Use when

  • vanilla for small surfaces, embeds, this course
  • a framework once three components share state and a team shares the code

👎 Think twice when

  • a framework for a single form
  • vanilla for a 200-screen product

🎨 Utility classes vs tokens + components — lessons 03, 08

⏮️ Before design tokens

Every page had its own blue, its own 13px, its own margin. Dark mode meant a second stylesheet nobody kept in sync.

✅ Merits

  • tokens: change --accent once, everything follows; dark mode is a swap
  • utility classes (Tailwind): fast to write, hard to drift, no naming debates

❌ Demerits

  • tokens alone still need components to avoid repetition
  • utility HTML gets long; the system lives in config, not in the CSS you read

👍 Use when

  • tokens under any approach — they are the uniform
  • utilities for teams that ship many screens quickly

👎 Think twice when

  • hard-coded colours anywhere
  • a second stylesheet for dark mode

🧭 Single-page app vs server-rendered pages — lessons 04, 12

⏮️ Before SPAs (~2012)

Every click reloaded the page from the server; forms lost their state; apps felt like documents. Then SPAs moved everything into the browser — and the first paint got slow and empty.

✅ Merits

  • SPA: app-like interactions, one shell, state kept between views
  • server-rendered / hybrid: fast first paint, works before JS, simpler caching, better for content

❌ Demerits

  • SPA: big bundles, slow first paint, SEO and a11y need care
  • server-rendered: full reloads unless enhanced; more server work

👍 Use when

  • SPA for tools people live in (dashboards, editors)
  • server-rendered or hybrid for content, forms, anything public

👎 Think twice when

  • an SPA for a blog
  • a full reload for every keystroke

♿ Accessibility — lesson 06

⏮️ Before accessibility was a checklist

Boards were built for one kind of reader: mouse, sighted, fast connection. Everyone else worked around them — or could not use them at all.

✅ Merits

  • semantic HTML gives keyboard, focus and announcements for free
  • the same semantics power tests and search
  • legal requirement in many places; the right thing everywhere

❌ Demerits

  • retrofitting is expensive; ARIA misused makes things worse
  • needs testing with real assistive tech, not just a linter

👍 Use when

  • always — it is HTML done right
  • every form, every custom widget

👎 Think twice when

  • ARIA on top of a <div> instead of using <button>
  • a11y as a final sprint task

🧪 End-to-end tests — lesson 10

⏮️ Before browser automation

Someone clicked through the app before every release and missed the one path that mattered.

✅ Merits

  • a real browser, real user paths — the highest confidence per test
  • catch integration bugs unit tests cannot

❌ Demerits

  • slow, flaky if written against class names, need a running stack
  • expensive to maintain in bulk

👍 Use when

  • a handful of golden paths (enrol a student) in CI
  • smoke checks on every deploy

👎 Think twice when

  • hundreds of e2e tests as the only tests
  • asserting on CSS classes instead of roles and labels

🚚 Static hosting vs a server for the front end — lesson 12

⏮️ Before static hosting + CDNs

Front ends were served by the same application server as the API — every page view hit it, every deploy restarted it.

✅ Merits

  • files on a CDN: cheap, fast everywhere, nothing to patch
  • cache-busting by hash makes deploys atomic and rollbacks trivial

❌ Demerits

  • dynamic per-user HTML needs a server or edge functions
  • routing for SPAs needs a fallback rule

👍 Use when

  • any board that is mostly the same for everyone — this whole School
  • dashboards that fetch their data from an API

👎 Think twice when

  • personalised HTML on every request
  • secrets baked into static files

🎽 A design system — lesson 08

⏮️ Before design systems

Each team drew its own buttons; the product looked like five products; every new screen re-decided spacing.

✅ Merits

  • consistency without meetings; tokens + components + rules
  • faster screens, fewer a11y regressions
  • designers and developers share one vocabulary

❌ Demerits

  • a system needs an owner and a release process
  • over-engineering for a single small app

👍 Use when

  • several teams or many screens
  • brand consistency matters

👎 Think twice when

  • a five-page site — tokens are enough
  • adopting a huge external system for two buttons
